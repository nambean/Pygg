# What Pygg changes: published benchmarks

> **Status:** Current · every published benchmark in one table, each figure linked to its report, and Pygg next to other gateways · reviewed 2026-11-20

Pygg is a local gateway between your coding tools and your providers. These runs measure what that changes, with real agents, real models and checks the agent cannot edit, and with a fault-injecting fake provider where a fault has to be repeatable. The runs to 2026-11-16 cost about $16.7, the overnight run of 2026-11-20 $16.10 and the repeat of the hard cases that day $7.21, within the budget in [ADR-028](DECISIONS.md#adr-028--mit-licence-a-20-benchmark-budget-and-no-auto-chat); the comparison runs added nothing. Each report gives its method, raw results and what it left out; read it before quoting a number. The harness is described in [benchmark/README.md](../benchmark/README.md).

## Where Pygg is worse

- **Throughput.** About 230 requests a second with 16 clients on one PC, because every attempt is written to disk before it is sent and settled after. LiteLLM [publishes](https://docs.litellm.ai/docs/benchmarks) 1,170 requests a second on four instances (its own test, D). Pygg is built for one person's tools, not for a team's traffic.
- **A provider that fails after it received the request.** By default Pygg does not retry a 5xx, a dropped connection or a timeout, because the provider may have run and billed it: the client gets the error (96% served with a provider failing every request, 0% with one dropping every connection). LiteLLM retries and falls back, and served 100% in both scenarios, each request after three attempts at the failing provider (M). Pygg's retry after a 5xx can be turned on per client (Clients → Limits); a dropped connection is never retried.
- **A provider that hangs.** Pygg waits up to 10 minutes for an answer to start and does not fall back on a timeout; LiteLLM waits too by default; with a 30 s timeout it tried the hung provider three times and fell back after about 91 s, leaving three abandoned attempts running at the provider (M).
- **A stream cut in the middle.** Pygg passes the break to the client (the client sees an incomplete answer, never a spliced one); it cannot continue the answer on another model. LiteLLM [documents](https://docs.litellm.ai/docs/router/learn/reliability) an opt-in continuation for plain text (D).
- **Prompt caching for Chat Completions clients** is something LiteLLM also does once configured (M, same result as Pygg).
- **Web sessions are slow by design:** a person's pace per site, short prompts and no tools ([PROVIDERS](PROVIDERS.md#the-guard) gives the numbers).
- **`auto/cheap` can choose a model too weak for the task** (2 / 6 on the real repository); `auto` with a tier floor is the default for agents.
- **Fewer platforms:** the desktop app is Windows x64 only; the command line and headless gateway are published for Windows, Linux and macOS, and not yet run on a Mac.

## What Pygg does not claim

- **No "60–95% fewer tokens".** Compression tools advertise that; an [independent replay](https://codepointer.dev/p/cutting-llm-token-costs-with-rtk) of 500 real Claude Code sessions found 3.7%. Pygg's savings come from keeping the provider's cache working, from cheaper models you choose, and from routing you can see (ADR-036 in [DECISIONS.md](DECISIONS.md)).
- **Not a quality benchmark.** Pass rates come from each case's own checks on a handful of tasks. They show that an approach did not break the work, not that one model is better.
- **Not a provider bill.** Costs are each gateway's ledger at list prices.
- **Not a ranking of other projects.** Rows marked D are what each project says about itself on one day; behaviour can differ from documentation, and every project changes.
