# How OmniRoute documents itself, and what Pygg should borrow

> **Status:** Reference · a study of OmniRoute's and 9router's documentation layout, with a proposed `docs/` layout for Pygg's open-source release · written 2026-11-13 · order: [ROADMAP](../../ROADMAP.md) · built: [Implementation Status](../../IMPLEMENTATION-STATUS.md)

This study is about documentation only. What Pygg took from OmniRoute's features, and what it rejected, is in [OMNIROUTE_FEATURE_RESEARCH.md](../OMNIROUTE_FEATURE_RESEARCH.md). Their text was read as data; nothing here is copied from it.

## Sources

- OmniRoute's root README (branch `release/v3.8.54`) and its documentation index `docs/README.md` (the index's own metadata says version 3.8.40, updated 2026-06-28), read on 2026-11-13 through the GitHub pages.
- 9router's root README (`decolua/9router`), read the same day. Its `docs/` folder was not reachable from the web (404), so only the README was studied.

## 1. What OmniRoute does

### The root README

The README is long and mostly marketing. In order: title and tagline, a headline of free tokens per month with a disclaimer, star and community links, a table comparing three patch versions, distribution badges (npm, Docker, Electron), jump links and 67 language flags, a three-step start (install, connect a provider, route through one endpoint) with a curl example, the promise and the "why", sponsors, the combos table, a comparison image, donations, an opt-in catalog, "What's New" per version, a grid of compatible coding tools, provider logos and counts, then the Documentation section, more install methods, contributing notes, security, privacy and licence.

What is reference rather than marketing: the combos table, the CLI list, the curl example, the install methods, and the Documentation section.

Installation is offered in this order: npm global install first (one command, then open the dashboard on a port), then Docker, Bun, source, pnpm, Arch, Nix, Podman. A table of "where it runs" adds desktop (Electron on three platforms), a macOS tray app, Android through Termux, a PWA, an OpenCode plugin and a VS Code extension. No desktop installer is offered for download in the README; desktop builds are built from source.

The README's Documentation section links documents in five groups:

| Group | What it links |
| --- | --- |
| Getting Started | user guide, setup guide, CLI tools guide, remote mode, Claude Code configuration, and the README's own quick start |
| Operations and Deployment | Docker, Podman, VM, Fly.io, Termux, PWA, uninstall, environment variables |
| Features and Architecture | architecture, compression (five pages), resilience, the auto-combo engine, proxies, free tiers, a features gallery, a codebase reference |
| Protocols and APIs | API reference, an OpenAPI file, MCP server and A2A server, each with a short README beside the code and a longer guide under `docs/` |
| Project and Quality | contributing, branching and release model, changelog, security policy, the translation guide, release checklist, coverage plan |

Troubleshooting has no section of its own in the README; the quick start links to a troubleshooting page for two known install problems. There is no FAQ in the README. The changelog is a root `CHANGELOG.md`; release notes are generated by GitHub at release time. The roadmap is a root `ROADMAP.md`. There is a comparison page but no methodology page; the counting rules for contributors and sponsors are stated inline.

### The documentation index (`docs/README.md`)

The index is grouped by intent and split by audience, with a one-line description per file:

- **For non-technical users:** `getting-started/` (quick start, auto-combo guide, providers guide, free tiers guide, web cookie guide, self-host guide) and `guides/` (setup, daily use, a features gallery, usage and quota, cost tracking, team cost centres, Docker, Electron, Termux, PWA, remote mode, headless, a master table of CLI integrations, one page each for OpenCode, Claude Code, Codex CLI and two other tools, management auth, the translation workflow, troubleshooting, uninstall).
- **For technical users:** `architecture/` (system design, codebase reference, repository map, authorization, resilience, quality gates, monitoring, design system, several ADR-like pages), `reference/` (API, an auto-generated provider catalog, removed providers, plugin manifest, OpenAPI, environment variables, feature flags, CLI commands, a free tiers directory), `frameworks/` (MCP, A2A, ACP, agent bridges, skills, memory, webhooks, evals, plugins and about fifteen more), `routing/` (auto-combo, quota sharing, reasoning replay and routing), `security/` (guardrails, compliance, stealth, two pages marked mandatory for contributors, token auth, egress, ban detection, CORS, MITM, supply chain), `compression/` (seven pages), `providers/` (one page per special provider), `comparison/` (one page), `ops/` (twenty pages of release, branching, merge train, runners, database, deployment and proxies).
- **Non-document folders:** `diagrams/`, `i18n/` (66 translated mirrors of the whole set), `screenshots/`, and `changelog/fragments/` for release notes in progress.

How status and version are marked: the index carries one version and one date at its top. Individual documents carry no status word. Inline markers do the work: **mandatory** on two security pages, "optional" or "off by default" on sidecars and the catalog overlay, "do not edit by hand" on the generated provider reference, and a warning on the removed-providers page.

What a newcomer reads first: the README's three-step start, then the quick start under `getting-started/`, then the provider guide, then the page for their coding tool. The index sets no numbered order; the non-technical section is the entry point and the folders do the rest.

### 9router, briefly

9router's README is its documentation. It has a three-step quick start (install from npm, connect a free provider, point a CLI tool at the endpoint), an ASCII diagram of its subscription-then-cheap-then-free order, a grid of supported tools, providers grouped by how they sign in (OAuth, free, API key, self-hosted) with notes on free tiers that have been discontinued, a features table with expandable details, a pricing table with an FAQ, use cases by persona, a setup guide with deployment and environment variables, available models by provider prefix, troubleshooting, the tech stack and a short API reference. Ten translated READMEs sit in `i18n/`. The repository has `docs/`, `gitbook/`, `DOCKER.md` and `CHANGELOG.md`, but the README does not link them; the website does the rest. No release version is stated in the README.

## 2. Pygg today

Pygg's documentation is engineering-first, and it is honest about status. `docs/README.md` was a flat table of 24 documents, each with a status word (Authoritative, Current, Reference, Historical, Withdrawn, Record) and a one-line description, followed by the status vocabulary and the writing rules. The root README has a four-step "How it works for a user", a long "What works today" list, the navigation table, the stack, how to build from source, the CLI, the licence and a pointer to the roadmap. CONTRIBUTING covers order, status, tests, schema, money, writing and commits.

What was missing for someone who did not build it:

- No page a user reads first. Install, first run, each coding tool, troubleshooting and the FAQ existed only inside the app's Guide, which cannot be read before installing, and partly in the README.
- The README's documentation pointer was one sentence, and it pointed at the engineering index. A user who opened `docs/README.md` met Implementation Status and the ADRs first.
- The index did not say who each document is for. A contributor, a reviewer and a user all read the same table.
- No changelog, no release notes, no comparison page, no page per platform (there is one platform today, so this last one is fine).

What Pygg already has that OmniRoute does not: a status word on every document; "built" that names its code and "verified" that says how; costs that are never shown as $0 when unknown; benchmarks with their method and raw results; decision records cited by number; reviews and their answers kept as written.

## 3. What to borrow

1. **A user path, separate from the engineering path.** One page that goes from the installer to "my coding tool uses `auto`", with troubleshooting and FAQ at its end. This is `docs/GETTING-STARTED.md`, written in this change from the README, the in-app Guide and Implementation Status. OmniRoute splits this over a quick start, a setup guide, a user guide and one page per tool; Pygg has one platform and three set-up tools, so one page is enough until it is not.
2. **An index grouped by reader.** OmniRoute's split is "non-technical" against "technical". Pygg's users are developers who use coding tools, so the split that fits is **user**, **contributor** and **reviewer**, each with a first-read order. Applied to `docs/README.md` in this change; file names and locations stay as they are, so links keep working.
3. **A Documentation section in the root README**, user documents first, then engineering, each with one line saying what it answers. Applied in this change.
4. **One page per coding tool** when the getting-started page outgrows itself. Later: `docs/user/CLAUDE-CODE.md`, `CODEX.md`, `OPENCODE.md`, `EDITORS-AND-SDKS.md`, with the getting-started page keeping only the short form.
5. **A root `CHANGELOG.md`** from the first tagged release, with the README's status block pointing at it instead of listing what changed. Until then Implementation Status is the record, and the dated reports under `docs/reports/` are the history.
6. **A root `SECURITY.md`** that points at `docs/SECURITY.md`. GitHub shows the root file in the Security tab and in the "report a vulnerability" flow. A one-paragraph pointer is enough.
7. **A comparison page, with its method.** OmniRoute compares itself to alternatives in one page without a methodology page. Pygg's rule is that claims carry their evidence, so a comparison page should say what was compared, on what date, with what data, and link the benchmark reports. The research under `docs/research/` is halfway there.
8. **Uninstall and "where your data is"** as sections of the getting-started page: the app data folder, the Credential Manager entries, each web session's profile folder. Done in this change for what the documents already say.
9. **Marking generated files.** `SCHEMA.md` is already generated and says so. `PROVIDERS.md` could later be generated from `presets.rs` the same way, with "edit the source, not this file" at its top.
10. **A quickstart examples folder** (OmniRoute has Python, Node, PHP and curl). Pygg's Guide has Python and PowerShell snippets; an `examples/` folder would let them be run and tested. Later.

## 4. What not to borrow

- **The marketing weight of the README.** A free-token headline, sponsors, donations, star history, badge walls and a per-patch feature comparison table do not fit a repository whose rule is "claims carry their evidence". Pygg's README keeps its status block with the three honest labels (built and live-verified, built and fake-tested, on hold).
- **Translated mirrors of the documentation.** 66 locales of 100-plus pages drift at once. Pygg's documents stay in English; the interface's Vietnamese translation comes last, and a Vietnamese README is a separate decision for the owner.
- **The size.** OmniRoute's `ops/` alone has twenty pages. Pygg adds a page when there is content for it, never a folder in advance. The proposed layout below names folders that will exist only once two or more pages belong in them.
- **Dropping per-document status.** OmniRoute marks nothing per file. Pygg keeps Authoritative, Current, Reference, Historical, Withdrawn and Record, and adds nothing to that vocabulary for users: a user page is Current or it is not published.
- **"Non-technical users" as the first audience.** Pygg's first user is someone running Claude Code, Codex or OpenCode. The getting-started page speaks to them.
- **Web-cookie guides as a headline path.** Pygg's web sessions are opt-in behind an account-risk warning (ADR-035), and one site suspended the owner's account for three days during a benchmark. They are documented in PROVIDERS.md and mentioned once in getting started, with the warning, not promoted.
- **A changelog before a release.** Nothing has been tagged. A changelog that starts at "0.1.0, everything" tells the reader nothing that Implementation Status does not.

## 5. Proposed `docs/` layout for the open-source release

Existing files keep their names and places (writing rule). New files are marked **new** (this change) or **later** (when the content exists).

```
README.md                      overview, status, how it works, a Documentation section (updated)
CONTRIBUTING.md                how to change Pygg (unchanged)
SECURITY.md                    later: a pointer to docs/SECURITY.md for GitHub's Security tab
CHANGELOG.md                   later: from the first tagged release
THIRD_PARTY_NOTICES.md
docs/
  README.md                    the index, grouped by reader (updated)
  GETTING-STARTED.md           new: install, first run, provider, each tool, cost, troubleshooting, FAQ
  PROVIDERS.md                 presets, endpoints, free tiers, live status; web-session sites
  SECURITY.md                  what is protected, what the user is trusted with, reporting
  user/                        later, when GETTING-STARTED outgrows one page:
    CLAUDE-CODE.md, CODEX.md, OPENCODE.md, EDITORS-AND-SDKS.md, CLI.md, TROUBLESHOOTING.md, FAQ.md
  reference/                   later: API.md (the three formats, x-smarttaskrouter-* headers), CLI.md
  COMPARISON.md                later, with its method and the benchmark reports it rests on
  IMPLEMENTATION-STATUS.md     authoritative: built and verified
  ROADMAP.md                   authoritative: order and gates
  DECISIONS.md                 ADRs
  ARCHITECTURE.md, SCHEMA.md, AGENTS.md
  ACCOUNT_API_ROTATION.md, CLI_IDE_NPM_PROVIDER_TIERS.md, OMNIROUTE_FEATURE_RESEARCH.md,
  RFC-2026-11-12-ORIGINAL-VISION-GAPS.md, SMARTROUTER_UI_UX_FUNCTIONAL_PLAN.md, UNIVERSAL_SHARED_MEMORY.md
  design/                      screens and the original sketches
  research/                    studies, this one included
  reviews/                     reviews and answers, as written
  reports/                     progress and release-check reports, as written
benchmark/README.md, benchmark/reports/
packages/npm/PUBLISHING.md     how the npm preview is published
```

### First-read order

**A newcomer who wants to use Pygg**

1. The root README's status block and "How it works for a user".
2. [GETTING-STARTED.md](../../GETTING-STARTED.md), top to bottom, stopping at their coding tool.
3. [PROVIDERS.md](../../PROVIDERS.md) when choosing a provider, for free tiers and which have answered live.
4. [SECURITY.md](../../SECURITY.md) before pasting a key, for where it is kept.
5. The in-app Guide, which repeats the steps with the commands ready to copy.

**A contributor**

1. [CONTRIBUTING.md](../../../CONTRIBUTING.md): order, status, tests, money, writing, commits.
2. [ARCHITECTURE.md](../../ARCHITECTURE.md): a request's path, a task's path, where to change what.
3. [IMPLEMENTATION-STATUS.md](../../IMPLEMENTATION-STATUS.md): what exists, and what is not verified, before touching it.
4. [ROADMAP.md](../../ROADMAP.md): whether the change is in order.
5. [DECISIONS.md](../../DECISIONS.md): the ADR that bounds the area, by number.
6. [SCHEMA.md](../../SCHEMA.md) and [AGENTS.md](../../AGENTS.md) when the change touches the store or the task engine.

**A reviewer**

1. [IMPLEMENTATION-STATUS.md](../../IMPLEMENTATION-STATUS.md), in particular "Not verified yet" and "Designed, not built".
2. [ROADMAP.md](../../ROADMAP.md), the P0 status table and the release gates.
3. [SECURITY.md](../../SECURITY.md), "Not covered yet".
4. [benchmark/reports](../../../benchmark/reports): each run's method, cost and raw results.
5. [reviews/](../../reviews): what earlier reviewers objected to and what was answered, so an objection is not raised twice.
6. [DECISIONS.md](../../DECISIONS.md) for the owner's decisions a review must not reopen (ADR-026, ADR-027, ADR-028).

## 6. Done in this change, and what is left

Done: this study; `docs/GETTING-STARTED.md`; the README's Documentation section; `docs/README.md` regrouped by reader with the first-read orders above.

Left for later, in the order they become possible:

1. A root `SECURITY.md` pointer (a one-paragraph file; any time).
2. One page per coding tool under `docs/user/` once the getting-started page passes about two screens per tool, or once a tool needs platform notes.
3. `CHANGELOG.md` at the first tagged release, and the README's status block pointing at it.
4. A per-platform install section when a macOS or Linux build exists (ADR-001).
5. A comparison page with its method, resting on the benchmark reports, when the owner wants one for the release.
6. `PROVIDERS.md` generated from `presets.rs`, so the table cannot drift from the code.
7. An `examples/` folder with the Guide's snippets as runnable files, checked in CI against the fake provider.
